# Testing and release gates

Run these from the repository root with Node.js 20 or newer:

```sh
npm test
npm run test:unit
npm run test:integration
npm run test:full
npm run static
npm run lint
npm run format:check
npm run test:ci
npm run coverage
npm run package:check
npm run release:check
```

The exact underlying commands are:

```sh
node test/run-suite.mjs unit
node test/run-suite.mjs integration
```

`npm test` runs unit tests then integration tests; `npm run test:full` currently aliases `npm test`. The runner discovers test files itself, so these commands work on Windows without relying on shell glob expansion. `test:ci` permits only its exact name-and-reason skip allowlist and fails both any other skip and loopback-backed skips. `coverage` applies the configured line/function/branch thresholds to `src/**/*.mjs`. `release:check` runs artifact cleanup, static syntax checks, lint, formatting, strict tests, coverage, and extracted-package validation.

## What the mock suite gates

The suite is deterministic and does not need a provider key. It covers config/key-reference validation, descriptor-checked config/installer/skill/storage reads and replacement detection, glob and path policy, temporary-index snapshots and reverse patches (including raw invalid-UTF-8 patch bytes and fail-closed invalid filename decoding), private linked-worktree creation/recovery/cleanup and Git-GC pinning, crash-safe transcript/artifact/job publication and recovery, terminal cleanup-attempt barriers, retryable and manual-cleanup records, cross-process durable cancellation, leases, redaction, pricing arithmetic, stale-read/concurrent-write/ignored-untracked tool behavior, provider SSE parsing/retries, agent-loop tool use, CLI argument forwarding, MCP discovery/dispatch and instructions, installer idempotence, package contents/extracted-package installation, job-list session scoping, working-tree health (read-only, filter-free, secret-name-free) and session spend, job lifecycle, integration conflicts, policy-only verifier consent, and process-group timeout cleanup. Loopback-backed mock-provider cases self-skip where the host policy blocks loopback networking; strict CI treats every such skip as a failure.

The OpenAI mock integration specifically proves handling of SSE comments and `[DONE]`, a usage record delivered in the final streamed chunk, fragmented tool-call arguments, replay of `reasoning_content` into the next request, 429/5xx retry behavior, fatal 401 behavior, request timeout handling, and mandatory `finish`. It proves our harness against the mock—not DeepSeek's production behavior.

Hung-stream regressions from the infinite-canvas Opus session exercise transports that ignore abort while awaiting headers or reading a response, including a body whose cancellation never settles. `test/unit/provider-deadlines.test.mjs` checks both adapters: the attempt timer aborts the request and returns `providerFailure.kind: "attempt_timeout"`; caller cancellation preserves its reason without retrying; late response bodies are cancelled. Anthropic error-body inspection is bounded and uses the same interruptible reader. `test/integration/provider-lifecycle.test.mjs` runs the Opus adapter through AgentLoop and JobManager with real leases, proving local and peer cancellation, provider attempt expiry, and both loop and manager wall deadlines release ownership before terminal completion. The manager watchdog fires at the remaining `timeoutMinutes` allowance without extra grace. JobManager tests pin `cancelRequested`, `cancelRequestedAt`, and `cancelRequestedSec` in full and compact waits and job reads, preserve the original timestamp on repeated cancellation, and clear pending-cancel output after completion. These tests use accelerated timers and mock streams, with no paid provider calls.

The Stock-Trading Opus session regressions cover three boundaries. Verifier declarations through a uv installation alias outside the canonical read/exec roots are refused before job creation, naming the resolved path to declare and use in `testCommand`; ordinary interpreter symlinks inside a granted venv/prefix remain supported. Specific HTTP/SSE provider transcript-corruption errors and the local `corrupt transcript: invalid interior JSON` failure may use `offload_continue`, retaining work, cumulative budgets and repair limits. Local restart keeps the malformed bytes in the transcript for audit, authenticates the entire file, and starts reading a fresh suffix; integrity failures are never bypassed. These cases live in the interpreter, provider, failure, store, and late-integration tests.

The 2026-10-21 Stock-Trading Opus transcripts also ended with ordinary Markdown summaries (1671 and 2507 characters), normalized provider reason `stop`, and no `finish` call. That is a completed provider turn, not an Offload completion; the loop deliberately records `no-finish` rather than inferring success from prose. The worker completion protocol now appears after repository conventions, explicitly requires invoking the registered finish tool next when work is ready, and directs blocked checks to concerns instead of a prose-only final answer; the finish tool description reinforces this. Prompt tests pin the final position and tool guidance for shell-disabled, server-verified, and report workers. FAILED and the original protocol error remain visible, and the report makes no claim that all requested edits are complete. Failed, unavailable, cancelled, timed-out, baseline-only, stale-round, mutated, already-applied, and otherwise ineligible results do not receive that recommendation.

Unresolvable targets are not reported. Previous session failures carry `inCommand`, and `drop`/`suggestedTestCommand` (or a `narrowing` reason) give the rewrite: literal operands removed, quoted `node --test` globs expanded, a plain `node` package script inlined, or pytest/vitest/jest exclusion flags. `test/unit/verifier-preflight.test.mjs` pins resolution and narrowing; `test/integration/failed-apply.test.mjs` covers the refusal, the declared glob, acceptance and the next-start suggestion; and `test/integration/apply-verify.test.mjs` proves on the real sandbox that the project-root `mkdtemp` fails in the verifier without the suggested `extraWritable` glob and passes with it.

## Credit exhaustion and retained-job recovery

The 2026-10-23 infinite-canvas incident left three worker jobs and report probe `oj-20261023-a1795800e8324374b1a518d72000e4d5` with HTTP 400 metadata and no fallback event. The retained adapter diagnostics contain only status/kind/attempts, not provider response bodies; the exact upstream refusal cannot be reconstructed from those records. Confirmed exhausted credits are evidence about the account, but do not prove that each HTTP 400 was a billing refusal. The former classifier recognized credit-specific codes, missed Anthropic's explicit balance message under `invalid_request_error`, and selected `error.type` ahead of `error.code`.

The adapter now recognizes the known sentence “Your credit balance is too low to access the Anthropic API.” only within an HTTP 400 `invalid_request_error` envelope, and recognized credit-exhaustion codes on HTTP 400/402 (including `error.code` behind a generic type). Authentication envelopes/statuses, unrelated HTTP 400, generic billing failures or credit mentions, network errors and partial streams cannot switch routes. Bodies remain bounded, ephemeral and absent from diagnostics. This is a regression fixture for a supported response shape, not a claim that the incident retained that exact body.

`provider_credit_fallback` is logged as a progress action with `creditFallback: true` before Flash spend. The durable marker appears in public results and the report names the snapshotted primary and fallback models. The original context and worktree are reused; a later continuation/repair reconstructs the provider on Flash. No job schema or transcript is rewritten. Flash remains limited by existing discovery, model-policy, trusted-price, thinking/high-effort and cumulative-budget gates. Unit tests pin classification and partial-stream/transport refusal. Core integration tests (now on the OpenAI -> Claude -> Flash chain) cover immediate refusal, refusal after an OpenAI edit and after a Claude edit, budget continuation on Flash, a Flash authentication failure with the original edit still captured in the retained diff, and refusal of a concrete Flash fallback with no trusted price before any provider request. Retained/static worker snapshots receive the same price check before a request.

OpenAI tier. `/offload_economy` runs latest GPT Terra -> latest Sonnet -> Flash and `/offload_premium` latest GPT Sol -> latest Opus -> Flash (profiles `sonnet` and `opus` are provider `openai` and fall back to `claude-sonnet`/`claude-opus`, then `flash`; key `keychain:offload-openai`, trusted table `openai-2026-10-26`). 2026-10-29: the order was changed to OpenAI first (previously Claude -> GPT -> Flash; the former `terra`/`sol` profiles were removed), and health reports `openaiFirst: true`. Fallback chains reserve each request's output budget at the costliest active or later eligible route (never an exhausted earlier route), since a later Claude route can cost more than the OpenAI primary. `doctor --live` probes the default profile's primary, which is now OpenAI. A config copied from an earlier example keeps its own Claude-first `sonnet`/`opus` chain. `node install.mjs` rewrites those two profiles to the current chain only when they exactly match a shipped shape (Claude -> Flash, or Claude -> `terra`/`sol` -> Flash with those profiles also unmodified); it adds `claude-sonnet`/`claude-opus`, keeps every other setting and the file mode, backs up the original bytes to `config.json.claude-first.offload.bak` (a later migration uses `.legacy-N`) and reports `configMigration` (`migrated`, `pending`, `reason`). It never rewrites, and never fails the install over, a config that would not validate afterwards (`invalid`), a symlinked, hard-linked or read-only file, or one whose `claude-*` profile the user already defines differently (`conflict`). Doctor (`config.legacyClaudeFirst`), the Claude session banner and repository health (`legacyClaudeFirst`, for every MCP client) name the remaining profiles with `fix: "install"` or `fix: "manual"` and the reason. To keep a Claude-first chain on purpose, define it under your own profile names so it no longer matches a shipped shape. Each hop needs that provider's explicit refusal before any output: for OpenAI, HTTP 429/402/400 whose JSON `error.code` is `credit_balance_exhausted` or `insufficient_quota` (or `error.type` `insufficient_quota`). `rate_limit_error`, spend-limit codes (`*_spend_limit_exceeded`, `organization_usage_limit_exceeded`), `slow_down`, 401/403, 5xx, network and partial streams never qualify, and bodies are never echoed into errors or logs. The official OpenAI endpoint uses the stateless Responses adapter (`POST /v1/responses`, `store: false`, `reasoning: {effort: "high"}`, `include: ["reasoning.encrypted_content"]`, `max_output_tokens`), because Chat Completions rejects function tools with reasoning there; a request capped below 1,024 output tokens (budget-finish and near-budget turns) runs with effort `none` so reasoning cannot consume the whole cap, and `doctor --live` probes that route at high effort with a 1,024-token cap. Encrypted reasoning is replayed without ids, stored byte-for-byte (not token-shape redacted), and counted in budget reservations only for routes that send it. The DeepSeek wire is unchanged. Discovery picks the highest `gpt-<major>[.<minor>]-terra|sol` by numeric version, not `created`; a release missing from the price table fails before spend. Every hop writes `provider_credit_fallback` with `providerStage` (durable `job.providerStage`, monotonic; `creditFallback: true` kept once stage >= 1) before spend on the next route, a double hop (Anthropic also exhausted) is allowed in one request, and a continuation or repair resumes at the persisted stage. Legacy records with only `creditFallback: true` resume at stage 1. Reports print one `provider transition: <from> -> <to>` line per hop. Public job details include `routes` (provider family and concrete model per snapshotted route, `active: true` on the current one; no endpoints or key references). Unit and mock tests cover all of this with stubbed fetch only; never run these against the real keychain or API.

## Platform gate

Run the normal suite on every supported host. CI runs the strict suite on Ubuntu with Node 20, 22, and 24, and on current macOS and Windows with Node 24. The release gate runs on Ubuntu Node 20 after those tests, with static, lint, format, strict-test, coverage, and package gates. The macOS sandbox integration test runs only when `sandbox-exec` can apply the generated restrictive profile; a present binary is not enough, because managed or newer macOS hosts can abort when applying it. Otherwise Node reports a documented skip. When it runs, it checks an out-of-scope write and Git-metadata access are blocked, including a linked-worktree Git pointer/common-directory path. Windows tests cover the ordinary AppData config path, fixed Credential Locker integrity-root behavior and credential stdin transport, `cmd.exe` command construction, environment scrubbing, and `taskkill` process-tree request through injected platform adapters. Installer tests cover default and overridden `CLAUDE_CONFIG_DIR`/`CODEX_HOME` locations, and tests that create a symlink are skipped on Windows only when Developer Mode/elevation is unavailable.

Linux and Windows are supported core/CLI/MCP/installer hosts, but their verifiers are policy-only: neither has a shipped OS sandbox. A macOS host whose `sandbox-exec` probe cannot apply the generated profile uses the same fail-closed mode. On Windows, install Git for Windows and Node 20+, and use `keychain:` or `env:` rather than POSIX-mode `file:` key references. On any policy-only host, a verifier is refused by default; only a caller-supplied trusted command with explicit unsafe policy-only consent can run, and it cannot repair. `offload_apply`'s `applyThenVerify` follows the same rule: it is refused on a policy-only host unless the call carries the explicit `unsafePolicyOnlyVerifier` consent.

Verifier temp directory and baseline-diff. A sandboxed verifier can write exactly one disposable per-run temp directory, exposed as `TMPDIR`/`TMP`/`TEMP`/`HOME`; `/tmp` and `/var/folders` are never granted, so a test that hard-codes them (or spawns a child with a cleared environment) fails by design and the job reports `VERIFY_ENV_FAILED` kind `temp-dir-denied`. The sandbox also sets `GIT_CONFIG_NOSYSTEM`, `GIT_ATTR_NOSYSTEM`, and (when installed) `DEVELOPER_DIR=/Library/Developer/CommandLineTools` to avoid reading denied host configuration. Some Git/Xcode installations still reach `/etc/gitconfig` or `/var/select`; a temporary-Git-fixture failure with that denial is reported as `VERIFY_ENV_FAILED` kind `git-config-denied`, an environment limitation rather than a product-test failure. Run that suite in the primary checkout; Git commands against the job's own checkout stay denied by design. `offload_job` health reports `verifierTmp`, produced by a real sandboxed probe; the runner tests assert the write set, the contract, and git inside the sandbox on macOS. The opt-in `verifierMode: "baseline-diff"` compares failing-test names (node:test spec/TAP, jest/vitest, pytest, go, cargo) between the result and an untouched snapshot run, and treats a jest suite that fails to run and a go `[build failed]`/`[setup failed]` package as their own new failures, and fails closed (`inconclusive`, `VERIFY_FAILED`) whenever it cannot prove "no new failures"; failure identity is lossless (a name past 160 characters keeps its head, tail and a hash of the whole, and per-run time directives such as TAP `# time=` are stripped), pytest ids may contain spaces and `N error(s)` count toward the summary, and parsing is bounded (suite nesting past 32 levels output past 32 MiB, or more than 10 s of parse time makes the run `inconclusive`); a run that stopped before running everything (pytest `Interrupted` at a collection error or `-x`/`--maxfail`, cargo's default fail-fast without `--no-fail-fast`, or a `-failfast`/`--bail` flag) is `inconclusive` (`stopped-early`) rather than a pass, because the worker's new tests may never have run; it still fails, with the named failures, when the result run stopped early after a new failure; `test/unit/verify-baseline.test.mjs` pins the parser against captured runner output and `test/integration/baseline-verifier.test.mjs` covers the lifecycle, including an end-to-end run with the real sandboxed Node.

Late apply verification is stricter still: `offload_apply` with `applyThenVerify` runs against the primary checkout with that checkout (including `.git`) unreadable and only a disposable temp directory writable. A test helper that creates a scratch Git repository but first inspects the primary repository can therefore fail with `repoPath must be inside a git working tree`. Do not broaden this sandbox: run that check yourself in the primary checkout and record its command/result with `verifiedBy` when calling `offload_apply`. A suite that only needs to write into the project tree (fixtures, `mkdtemp` under the project root) can pass `applyThenVerifyIn: "scratch"`: the command then runs in a disposable private worktree of the just-applied primary tree, writable except `.git` and `node_modules`, still sandboxed with no network, and the outcome is recorded and reverted exactly as in the primary; `test/integration/apply-verify.test.mjs` covers the copy's contents and removal, revert on failure, and on macOS the same project-root `mkdtemp` failing in the primary and passing in scratch.

Declared Python interpreter. The verifier profile reads nothing outside the worktree, the per-run temp directory and the system toolchain, so a `testCommand` that runs a virtualenv's `python` fails with `Operation not permitted` (even a system CPython dies at startup unless the root directory node's metadata is readable). `verifierInterpreter` (absolute paths of a virtualenv root or interpreter, at most four) is resolved by the server in `src/verify-interpreter.mjs`: it is refused when it is a script or shim, sits in the job's writable scope, or lies in a credential, home or host-configuration area (or outside the optional `verifier.interpreterRoots` allowlist in the server config), and otherwise grants the verifier (and `applyThenVerify`, never the worker's `run_command`) read and exec of that root and its base Python installation, never write; the credential conventions are re-anchored at each root. `offload_job` health reports `verifierPython`, and a `verifierInterpreter` argument runs `python -c` inside the sandbox first. Optional `verifierImports` names up to 16 dotted modules to import during that health probe; the version result is marked so module startup output cannot replace it. A native import crash is classified and preserved in the public job report, while a failed import probe returns `partial` before a job is started. `test/integration/verifier-interpreter.test.mjs` builds real virtualenvs and asserts against the live sandbox that the declared one runs (stdlib imports, `-m`), that a second, undeclared one and its sibling files stay denied, and that neither the venv nor its base installation is writable; `test/unit/verify-interpreter.test.mjs` pins the resolution and refusal rules. Installed-skill staleness is the same kind of drift check: health compares the skill copies a client reads with the skill hash the server was built with (`server.skill`, `staleSkill`), through the function the session-start hook uses, and `test/integration/skill-health.test.mjs` drives it with temporary `HOME` directories holding stale and fresh copies, including the real `offload mcp` process.

Turn-budget sizing. A worker scans a file one `read_file` page (24,000 rendered characters, including the truncation marker) at a time, so a 14k-line file costs about 31 read turns before any edit. When the caller omits `budget.maxTurns`, `src/budget-sizing.mjs` stats (never reads) the files in `relevantPaths`, the literal `ownedPaths` and report inputs through the same `PathPolicy` the worker uses, and recommends `ceil(1.25 x (6 + 4 + reads + 2 x owned))` turns; the stored cap is `max(configured default, min(recommended, 200))`, so USD (`budget.maxUsd`) is the effective ceiling. An explicit `maxTurns` is honored exactly and warned about when below the recommendation; `budget.turnPolicy` (`auto`|`fixed`) overrides either default. `offload_start` echoes `budgetSizing`; a `BUDGET` stop records and reports which cap tripped (`budgetStop`, from the loop's `budgetCap`) without touching the reservation estimator, so small explicit caps still stop on BUDGET by design. `offload_continue` with `extraTurns` refreshes the stored `budgetSizing` (`raiseBudgetSizing`: new cap, source `raised`, warning recomputed), and the report's `turn budget:` line appears only on a `BUDGET` stop whose recorded `budgetStop.cap` is `turns` and whose record still matches the job's cap (a USD or reservation stop is not explained by the turn cap). `resolveTurnBudget` also checks the expected turns (`min(cap, recommended)`) at 45 s each against `budget.timeoutMinutes` and never changes the cap for it: a caller-chosen timeout only gets a warning (the job will probably end `TIMEOUT` before its turn cap), while an omitted one (Core passes `timeoutScalable`) is scaled up to the needed minutes, bounded by `AUTO_TIMEOUT_MAX_MINUTES` (120), stored in the job's budget and echoed as `budgetSizing.timeoutMinutes`, with a warning when even the ceiling falls short; a plain `relevantPaths` entry for a file is a whole-file read hint that widens any `:START-END` range on it (an `ownedPaths` mention never does) and glob entries are never statted; the 200 automatic ceiling is pinned by a literal. `read_file` scans from byte zero whatever the offset, so a server-computed window offset reveals nothing a whole-file read would redact (`test/unit/tools.test.mjs`). `relevantPaths` entries may carry `:START-END` line ranges, which the worker prompt turns into a server-computed `read_file` byte offset (`LocalTools.lineByteWindow`, a server-only method absent from the advertised tools). `test/unit/budget-sizing.test.mjs` pins the formula against the real page count of 733,780-byte and boundary files, so a change to the read page size fails it; every worker prompt also carries the standing falsifiable-assertions rule (`test/unit/prompt.test.mjs`).

`offload_apply` with `applyThenVerify` applies a reviewed diff, runs the caller's command in the primary checkout under the sandbox with the checkout read-only, and reverts through the ordinary revert machinery on any non-pass; `test/unit/apply-verify.test.mjs` pins the outcome classification and the output tail (linear on unterminated escape sequences), and `test/integration/apply-verify.test.mjs` covers ordering, lease, cancellation, concurrent edits, revert failure, an unexpected failure right after the apply (settled from the live tree), a bounded redacted journaled command, one redaction for the returned and stored output tail, retiring a stale outcome once the primary re-applies, reverts by hand, or repairs or continues the job, the job's own `denyRead` reaching the command, crash recovery from the journal, a journal this process orphaned (settled by wait, revert, apply or recovery, while a genuinely foreign live owner is left alone), another process's `offload_cancel` stopping the command, no network whatever the job's `allowNetwork`, the `UNSANDBOXED` label following what actually ran, and (on macOS) a real read-only sandboxed command.

Applying a FAILED job. A worker that did correct work and then ended FAILED (a repeated finish-protocol violation, a loop, no finish, a provider fault, a restart) no longer forces a hand-applied `patch.diff`. `offload_apply` accepts any FAILED cause, but only through `failedApplyRefusal` (`src/failure.mjs`), the one gate `JobManager.apply()` and the report's `apply` next action share, which refuses a report job, an applied or reverted diff, an unresolved integration/revert outcome, a manual-cleanup record, a lost lease, a diff that held a configured secret, any scope or verifier-authorship violation, a missing scope audit or result snapshot, an empty diff, and a retained diff stamped (`patchRound`) with an earlier round than the one that failed (a repair or continuation whose own capture failed). The manager then proves the stored `revert.diff` passes the store's digest check, is non-empty and equals the diff between the recorded baseline and result snapshots over the owned paths, and runs the same conflict, lease, branch/HEAD, index and owned-path-only checks as every other apply status. The result is `DONE_UNVERIFIED`, and `appliedUnverified.failure` keeps the original failure kind and reason for the report; `applyThenVerify` reverts a failing check and leaves the job FAILED and apply-eligible. CANCELLED jobs are never eligible; `offload_repair` and `offload_continue` are untouched. `test/integration/failed-apply.test.mjs` drives a real isolated-worktree manager through dry run, apply, revert, every failure cause, an empty diff, a scope violation, a primary conflict, a moved HEAD, a drifted index, single-flight leasing, each outstanding-state refusal, tampered artifacts and snapshots, a continued round (and a secret-bearing third round), `applyThenVerify` revert-then-pass, a CANCELLED refusal and a crash-recovered job; `test/unit/failure.test.mjs` and `test/unit/report.test.mjs` pin the gate and the report line, and `test/integration/mcp-e2e.test.mjs` runs the finish-protocol case over the real MCP server.

Snapshot/finalization recovery. Temporary-index snapshots use plain `git add -A`, then remove excluded literal entries with NUL-delimited `ls-files`/`update-index`; an exactly gitignored `node_modules` symlink must work on Apple Git as well as an unignored server link. Git stderr is bounded, control-stripped and redacted through `E_WORKTREE_SNAPSHOT` and the finished event's `finalizationError`. Finalization saves the audited diff and tree metadata before pinning durable refs. If capture, artifact storage or pinning fails, `workspaceRetained` prevents normal and startup cleanup from deleting worker files. After fixing the underlying error, `offload_apply` (dry run first) recaptures and audits the workspace, saves both diff artifacts and pins the trees before cleanup; all existing integrity, scope, verifier-authorship, branch/HEAD, index, conflict and verification-evidence gates still apply. Repair/continuation waits for this capture so it cannot replace an uncaptured workspace. Configured-secret patch rejection keeps its existing refusal and cleanup behavior. Unit tests cover the ignored symlink, index/HEAD preservation and Git diagnostics; failed-apply integration tests inject real corrupt Git config, ref locks and an artifact-write failure, prove recovery retains paid work, apply after fixing the fault and pruning Git objects, and reject scope/verifier mutations without rerunning the worker.

Loop-failure diagnostics. When the loop guard stops a worker (`Loop detected: identical failing tool calls repeated 3 times`), the loop result carries a closed `failureKind` and a bounded `toolFailure` (`src/failure.mjs`): the first failing call of the turn (tool, an argument summary in which file bodies are only a size, and the real error) after key-aware redaction, control stripping, path-aliasing (`<worktree>`, `<repo>`, `~`) and a 300-character clip. The worker is still shown only `TOOL_ERROR: Tool execution failed`, plus at most a fixed hint chosen from a closed, anchored table over the tool's own messages (edit and stale-read state, size limits; never a missing path, an out-of-scope or Git-ignored write, or a policy refusal, because policy refuses before the filesystem is touched and any hint that differed between those would let a worker probe for protected paths); no part of the message is echoed. `no-finish`, `output-cap` and `finish-protocol` FAILED rounds carry a kind too; every other FAILED cause carries none. The manager persists the kind only for a plain worker-side FAILED (never over a provider failure, lost lease or bad accounting), keeps a report job's call down to `{tool, turn, repeats}`, and resets both with the error each round. `continuableFailure` is the one default-deny gate shared by `offload_continue` and the report's `next:` line: status FAILED, a durable kind whose canonical error text is still the job's `error`, and no provider failure, scope or verifier violation, moved branch, integration/cleanup state or applied diff. A continuation replaces the generic cap text with the failing call (plus the same fixed hint, never the recorded error) and "do not repeat it", needs no cap increase, and is refused once the same call (`priorLoopSignature`) loops again. A provider `content_filter` stop with no tool call is FAILED without a `failureKind` (a re-send recurs), and the loop guard counts repeats per call, not consecutive ones, so the report says "failed Nx". A `finish` call that shares its turn with other calls, or whose arguments are invalid, is never run and neither is anything beside it: the loop answers every tool call of that turn with one fixed `TOOL_ERROR:` result (the prefix keeps a refused `write_file` from reading as a landed write on resume) in one atomic durable batch, appends no provider-controlled text, and lets the worker retry once per run. The retry is an ordinary turn (it counts against `maxTurns`, needs one left, and keeps every reservation, timeout and accounting check) and is withheld from the finish-only budget recovery. A second violation, or one on the last turn, ends the round FAILED with `failureKind: 'finish-protocol'` and the unchanged text `finish must be the sole valid tool call in a turn`; that kind is continuable, and its continuation task says to call finish alone after any remaining work. `offload_job include:"log"` first folds consecutive progress events that differ only in turn, usage, cost and latency (one repeating event, or a repeating cycle of up to 8 of them, which is what a worker looping on one call writes) into one `progress-repeat` line (`[provider_request_pending > provider_usage > tool > read_file] x3 (first..last)`, with the folded event count, turn range and slowest phase) before the window is applied: `tail` counts folded lines, `logInfo.lines` is the folded count and `logInfo.rawLines` the stored one, while the digest's counts and recent events describe the stored log. The digest drops `needsDiagnosis` once `lastFailingCall` is known. `offload_job include:"log"` is windowed, and `tail`/`limit` without a jobId are rejected by Core and the manager alike (`tail` 0-1000 events, `limit` 2,000-60,000 characters; defaults 60 and 16,000, never cutting inside an event, with a `logInfo` summary; store secrets and token shapes are redacted from the digest and each event before the window is measured, so `limit` is a hard ceiling, and a log line that is valid JSON but not an object counts as unparseable instead of failing the read). Tests: `test/unit/failure.test.mjs`, `test/unit/diagnostics.test.mjs`, the loop cases in `test/unit/loop-hardening.test.mjs`, the continue matrix in `test/integration/late-integration.test.mjs`, a real worker loop through Core in `test/integration/core-routing.test.mjs`, and the finish-protocol and looping-worker log scenarios over the real MCP server in `test/integration/mcp-e2e.test.mjs`.

Before a macOS release, manually exercise the intended toolchains (for example npm, pytest, cargo, and Go) in a narrow sandboxed job. The existing test suite does not prove all toolchain cache paths, dependency installs, or network behavior.

## Updating a local installation

Editing this checkout does not update a previously installed MCP package or its client skill. Reinstall from the source checkout into the same prefix used by the active MCP registration, then run that installed package's installer so its registration and skill artifacts come from one version. For the standard macOS local installation shown by `offload doctor` or the Claude MCP registration:

```sh
(
  set -eu
  offload_prefix="$HOME/.local"
  offload_pack_dir="$(mktemp -d "${TMPDIR:-/tmp}/offload-pack.XXXXXX")"
  cleanup_offload_pack() { rm -rf -- "$offload_pack_dir"; }
  trap cleanup_offload_pack EXIT HUP INT TERM

  npm pack --ignore-scripts --pack-destination "$offload_pack_dir"
  set -- "$offload_pack_dir"/*.tgz
  [ "$#" -eq 1 ] && [ -f "$1" ] || { echo "expected one offload package archive" >&2; exit 1; }
  offload_tarball="$1"

  npm install --global --ignore-scripts --prefix "$offload_prefix" "$offload_tarball"
  node "$offload_prefix/lib/node_modules/offload/install.mjs" --skip-key --clients=claude,codex,cursor
  node "$offload_prefix/lib/node_modules/offload/bin/offload.mjs" doctor
)
```

The subshell always removes its freshly created temporary package directory, including on interruption. Installing the packed tarball (rather than the checkout path) matters: npm can globally link a directory, and the installed installer then resolves that link back to the source checkout. A tarball produces a real package copy, so its installer, MCP registration, and skill artifacts all come from the same installed version. After an update, the installer prints `restart.required`; restart every running Claude Code/MCP client before making a report/input-files call. It deliberately never kills or hot-reloads a live client process. Confirm the next `offload_job` health response has the expected server version/build/skill hashes, schema revision, report/input-files capabilities, and sandbox reason. If health looks stale, compare that server identity with the startup hook's runtime version/build and schema output after restarting. Use the actual registered prefix/path instead of assuming this example when a different package location is active. Confirm the installed package's `package.json` version and, for an unreleased local build with the same version number, compare the changed source artifacts before claiming it is current. Do not hand-edit `node_modules`; reinstalling keeps the package, MCP registration, and installed skill in sync.

Current installers write skill recovery copies under each client's `offload-backups/` directory, outside skill discovery (for example `~/.claude/offload-backups/SKILL.md.offload.bak`). Distinct command contents or later revisions receive `.legacy-N` suffixes; identical repeated contents reuse the existing recovery copy. Client state reads are bounded to 16 MiB and package/config migration reads to 1 MiB, using checked descriptors and a fixed allocation so a growing file cannot defeat the limit. An install or update also safely migrates a regular legacy adjacent `SKILL.md.offload.bak` into that directory without replacing an existing recovery copy. Do not manually move a normal legacy backup: run the installed package's installer instead. If an unsafe or unmanaged legacy path remains—for example, a symlink, non-text file, or a file changed during migration—the installer deliberately leaves it untouched; inspect it without following it, then manually move it outside `skills` or delete it only after confirming it is no longer needed. Never treat a recovery copy as an active skill.

## Delegation behavior eval

Use stubbed MCP tools and the installed skill/pointer to test each local host with these prompts. Only an actual `/offload_economy <task>` slash command is a positive routing case; no ordinary prose selects Offload:

2. **Indirect multi-file work:** “Can you take care of this refactor and make sure it is tested?” It must not discover a delegation route merely because the work is bounded, multi-file, implementation, testing, or debugging work.

4. **Mention, quote, or negation:** “Do not use `/offload_economy`; implement this yourself.” It must not select Offload. Repeat with a quoted or discussed `/offload_economy` command and confirm that neither form invokes it.
5. **Sonnet Ultracode:** “Use Sonnet Ultracode to implement this feature.” It must remain a normal Claude Code request and must not load Offload or suppress Claude Code's native-agent workflow.
6. **Tiny edit:** “Fix this one typo in one file.” It must not load Offload or introduce delegation overhead.
7. **Explicit slash route:** “`/offload_economy` Implement the requested multi-file feature and tests.” It must load Offload, use `offload_start` rather than a native Claude subagent, and pass `profile: "sonnet"` while omitting `effort`.
8. **Pro is unreachable:** “`/offload_economy` Delegate this hard multi-file refactor with profile `pro`.” `pro` is not a configured profile and cannot become one, so Offload must report `unknown profile: pro` (or the agent must use `flash`) and never pass or invent a Pro model id.

`sonnet` is the default logical routing profile, not a synthesized provider model name. It discovers and snapshots the newest supported concrete GPT Terra at each local job start, with the latest Anthropic Sonnet as its first fallback. On each provider's explicit credit-exhausted refusal before output, it switches permanently for that job to the next route, ending at the `flash` profile, which discovers and snapshots the provider-maintained `deepseek-flash` route from DeepSeek's Models API. A failed discovery or unknown selected price aborts before spending; network/auth/rate-limit failures and partial responses never trigger fallback. Pro is deliberately unreachable: `src/model-policy.mjs` rejects any Pro model spelling, and any model other than `deepseek-flash` on a `deepseek.com` endpoint, in config validation, execution snapshots, job accept/run, and the provider constructor and per-request override; the shipped pricing table has no Pro entry, so a Pro response model is unauthorized under a finite budget.

For every positive case, assert an explicit repository path when the client has no workspace root, a review/verification step before completion, and no state-changing Claude call without the host's normal approval. On a policy-only host, assert that the client does not silently opt into `unsafePolicyOnlyVerifier`: it should omit a worker `testCommand`, review the result, and run its own relevant checks before completion unless the user specifically authorized the narrow unsafe verifier exception.

Ordinary doctor performs no network request. The latest explicitly authorized DeepSeek live smoke used a disposable synthetic fixture and completed `DONE_VERIFIED` in three turns. Its configured and returned model was exactly `deepseek-v4-pro` with effort `high`. It reported input `3911` = cache hit `2560` + cache miss `1351`, output `463`, and an estimated successful-job cost of `$0.00186472`.

The worker had no network access, made exactly one scoped synthetic-file edit, and recorded no policy violations. The server verifier and independent tests both passed. The fixture was reviewed and deleted after the run. This host was policy-only, so file tools were available but no worker shell command was run. `DONE_VERIFIED` came from the narrow, caller-supplied trusted verifier exception (`unsafePolicyOnlyVerifier: true`), not from general OS sandboxing; that exception cannot trigger repair.

That live run also verified the DeepSeek usage compatibility fix: the provider accepts nested `cached_tokens` and `prompt_cache_hit_tokens` only when both are well-formed and equal, and rejects malformed or conflicting duplicate values before usage is persisted. Known metered spend for the successful job plus a prior failed retry was `$0.010786908`; an earlier failed response may have incurred a small additional unknown cost because its invalid duplicate usage was rejected before persistence.

These are deliberately narrow results. They demonstrate one verified end-to-end edit and this specific production usage-field behavior, not general tool reliability, cache rates or semantics, model pricing, rate limits, concurrency, or general reliability. Use only a disposable configuration, retain only redacted aggregates, and check [Spike 02](spikes/02-openai-surface.md). The mock tests still prove harness mechanics, not production behavior.

Wall-clock accounting. `src/timing.mjs` splits each round into queue, setup, startup, provider, tool, verify, finalize and other time, driven by the progress events the manager already receives plus one tool-phase marker and per-call tool timings from the loop. The buckets add up to the round's active time by construction (a round is always in exactly one phase), a request still open is attributed but not counted as a completed call, and the record is stored per round (`job.timing`, at most eight rounds, closed shape via `sanitizeTiming`). A running round's phase and last event are in `job.activity` (a manual repair or continue stamps phase `setup` while it recreates the isolated workspace, so that wait is judged too); there is deliberately no turn-cap projection, because the cap is a ceiling a worker normally finishes well under, so only the wall-clock share (80% and 95% of `budget.timeoutMinutes`) warns about the allowance; `assessStall` judges it against limits the job carries (attempt timeout, a command's own timeout, `budget.timeoutMinutes`, the verifier's time limit) and `offload_wait` returns the result as `progress.stall`, once per new (kind, level), so the `unchanged` marker still collapses repeated polls (`offload_job` returns the same advisory as a top-level `stall` field and a `stall:` report line). The worker's `run_command` timeout is capped at 900 s (a larger integer request is clamped to the cap rather than rejected, since the rejection has no closed hint and a re-sent call would trip the loop guard; non-integer or negative values are still rejected); a batch runs its commands one after another, so the tool-phase marker carries the sum of their timeouts (capped at 64 x 900 s) and the stall check judges the batch against that sum. A round relaunched by recovery after its owner died carries the earlier owner's record into its clock (`RoundClock` `carry`), books the unobserved gap as other time, and keeps the original queue and setup figures, so recovery is never reported as queue time. Tests: `test/unit/timing.test.mjs` (clock arithmetic, sanitising, every stall threshold), the `time:` and `stall:` report cases in `test/unit/report.test.mjs`, the marker/timing cases in `test/unit/loop-hardening.test.mjs`, the keep-alive-drip pin in `test/unit/provider-sse.test.mjs` (a provider cannot stretch one attempt past its timeout), `test/integration/timing.test.mjs` (a hand-driven clock through the real manager: queue, setup, repair rounds, a dying or cancelled worker's finalization time, a recovered round, a fractional clock, stall dedup in `wait`), and a real worker loop through Core in `test/integration/core-routing.test.mjs`.

Job list detail. Each row of the no-argument `offload_job` list (and so of `offload job`, which prints the same rows) carries a one-line summary of the brief next to its status and cost: `task` is `redactedSummary` (`src/redact.mjs`) of the stored brief, redacted before it is clipped to 100 characters (credential shapes, assignments, configured literal secrets, home paths read `~`), then the latest round's `startedAt`, `finishedAt` (terminal jobs only) and `durationSec` (finished minus started, or elapsed so far with `running: true` while active). A queued or requeued job has not been claimed this round, so it shows no clock rather than the previous round's. `costUsd` is the list's existing cost source, rounded; an unknown cost stays `null` and is counted in `listing.costUnknownJobs`, never 0. Tests: the rows cases in `test/integration/job-listing.test.mjs` (a terminal, a running, a queued and a never-started row; a poisoned brief with a secret placed across the clip; an unknown cost) and the running-row case in the stalled-provider scenario of `test/integration/mcp-e2e.test.mjs`.

Retrospective. `offload_job` with `include: "retrospective"` (no `jobId`; optional `jobIds`, at most 16, default every job of this server session) and the CLI `offload retrospective [--jobs id,id | --last N]` return one bounded, redacted evidence digest for improving Offload itself, built by the pure `src/retrospective.mjs` from stored job records, bounded lifecycle events, and health: per job its id, mode, profile, status, verdict, failure kind and last failing call, verifier environment kind, the cap that stopped it, turns, spend (`null` when unknown), the timing breakdown, rounds and continuations, the apply path (server-integrated, `applyThenVerify`, or the primary's own `verifiedBy`) and a 100-character redacted task summary; the health facts (stale server or skill, verifier sandbox, `verifierTmp`, `verifierPython`, `verifierDeps`, dirty tree); totals; and a closed list of `signals`, each a stable code with a one-line evidence string. The codes are `protocol-failure-finish`, `output-cap-failure`, `loop-without-diagnostic`, `verify-env-failed:<kind>`, `repeated-env-failure`, `python-verifier-unavailable`, `budget-stop-low-spend` (a server-sized turn cap that left most of the dollar cap unspent; a stop on a cap the caller chose, or on the dollar cap, is by design), `repeated-turn-cap`, `turn-sizing-outlier`, `repeated-continuation`, `late-verification`, `wasted-spend-on-failed-job`, `stall-warning`, `apply-without-server-verification`, `stale-skill-ignored`, `stale-server-ignored`, plus context that never makes a prompt worthwhile (`cancelled-by-user`, `provider-failure:<kind>`). The four efficiency signals are emitted only with server sizing provenance, never for a caller-fixed cap, cancellation, provider or finish-protocol failure, or absent sizing evidence. Their evidence includes the actual and recommended turns, ratio, sizing source, cap count, continuation count/statuses, or verifier round as applicable. `DONE_VERIFIED` remains a correctness success: these signals describe efficiency, sizing, or worker-completion friction only. `maintainerPromptWarranted` is true for ordinary attributable signals, for `repeated-turn-cap`, or when `turn-sizing-outlier` and `repeated-continuation` both occur; a lone sizing outlier or continuation is context rather than a prompt threshold. Thus a correct result can still warrant maintenance when it repeatedly exhausts the automatically sized budget, while a weak/thin brief, a caller-fixed cap, a failing suite, a cancel, a provider failure, or a finish-protocol failure does not. `maintainerPromptSkeleton` is the prompt a user can paste into the session that maintains Offload, in their own shape: a header naming the project (repo name only, never its path) and profile and the absolute path of the Offload checkout the server runs from (the one absolute path anywhere in the response), an `Evidence:` list from the signals, a numbered `Please:` list from a closed table (one request per signal family, never free text) and the standard closing line. Efficiency requests explicitly ask the maintainer to investigate worker focus, budget sizing, or completion discipline. The digest is at most 6,144 bytes and the skeleton 4,096 whatever the input (large sessions are cut jobs-first, then signals, and the cut is counted in `omitted`; the verdict is computed before any cut), holds no source, diff or brief beyond the summary, and every string passes redaction and path relativization a second time on the way out. The primary reads the signals as leads, adds what it had to do by hand and decides whether to emit the prompt; nothing edits the repository or the configuration. It is read-only apart from one line appended to `retrospectives.jsonl` beside the diagnostic log (`$XDG_STATE_HOME/offload`, mode 0600, the redacted digest without skeleton or brief, 192 KiB with one rotation, history reads and writes off with `OFFLOAD_LOG=off`, never sent anywhere); `offload retrospective list` counts how many stored retrospectives raised each signal and `export` prints them, and the terminal form records nothing. Runtime identity reports `retrospective: true` (additive, no schema revision bump). MCP only: the digest is an `include` value of the existing read-only tool, so it needs no new approval; `jobIds` is not offered on the CLI `job` command, which has `retrospective` for it. Tests: `test/unit/retrospective.test.mjs` (each signal code with a positive and a negative case, including successful-but-inefficient and caller/provider/protocol safeguards, the attributable rule, per-job facts, the skeleton's shape, poisoned input, size bounds, stored records and aggregation; every one of these was also checked to fail under a deliberate mutation of the rule it pins), `test/integration/retrospective.test.mjs` (session, named and newest scopes through Core and the manager's operational-view reads, validation, multi-repository merge, the history file's mode, rotation bound, symlink refusal and re-redaction), the retrospective cases in `test/integration/mcp.test.mjs` (schema, routing, refusals, skill and CLI coherence), `test/integration/cli.test.mjs`, and through the real `offload mcp` process in `test/integration/mcp-e2e.test.mjs` (a failed finish protocol applied by hand, a clean job that warrants nothing, the temp-dir verifier failure and a baseline-verified job, a live stall, redaction and size, and the history read back by the CLI).
