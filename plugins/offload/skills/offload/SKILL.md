# Offload protocol

You are the architect, orchestrator and reviewer. Built-in jobs run in a private linked worktree seeded from an exact snapshot of the primary checkout; the worker never commits, pushes, or switches branches. Only successful owned changes may later integrate after primary-checkout conflict checks. The snapshot is the primary checkout as it is right now, including uncommitted work: staged and unstaged tracked changes, deletions, and untracked files that are not gitignored. Gitignored files are not copied; only a read-only `node_modules` link is provided. Your index, HEAD and files are never changed. A dirty tree therefore does not block a job: the worker starts from your dirty state, and the job diff is relative to that snapshot, so it never contains your own uncommitted edits. An untracked file that is not gitignored is part of the snapshot even if it is secret-shaped, so gitignore it first. Do not edit an owned path in the primary while its job runs. Respect “solo”, “no offload”, or “do it yourself”: do the work directly.

Workers cannot use the primary session's live MCP connectors or other client tools. On a policy-only host they also have no worker shell; they can only use their file tools in the permitted private worktree. Primary Claude must review the resulting diff or reportResult and perform the appropriate verification before its final answer.

## Routing contract

Use this Offload MCP service only when the user invokes `/offload` as a slash command (for example, `/offload <task>`). Do **not** satisfy that `/offload` command invocation with Claude Code's native subagents. A mention, quotation, negation, or discussion of `/offload`, offload, delegation, **DeepSeek** / **DeepSeek-V4.1-Flash**, a provider, or a model does not select Offload, nor do bounded, multi-file, implementation, testing, debugging, Workflow, ultracode, or native-subagent requests. The primary Claude session keeps architecture, decomposition, security decisions, integration decisions, broad verification, and the final review.

**Precedence:** for a `/offload` command invocation, the command or an accompanying explicit user instruction not to use native subagents overrides session-level modes or prompts that suggest Workflow, “ultracode,” or native subagents. A standalone instruction not to use native subagents does not trigger Offload; work directly unless the user separately invokes `/offload` as a slash command. Otherwise this skill does not apply and Claude Code may use its ordinary routing, including Sonnet ultracode/native-agent workflows. Never invoke Workflow or a native subagent for that `/offload` command invocation.

Before creating a job, decide whether a worker can actually do it. Work that needs a live MCP connector, authenticated client integration, interactive browser/app access, or another primary-only tool must be done directly by the primary session. Likewise, do straightforward no-change work directly unless it is an explicitly supported Offload report/analysis job with all of its inputs already available to the worker. Say that no worker was started rather than silently running zero jobs.

**When Offload pays off.** It saves primary-session usage only when the worker's own loop (many cached file reads and tool turns) is much larger than what you spend writing the brief and reviewing the diff. Good fits: bounded, well-specified, parallelizable, or test-heavy packages. Poor fits, which you should do directly:

- Small known edits (roughly under 40-50 changed lines): the fixed per-job overhead (brief, job round-trip, diff review) costs the primary more than the edit.
- Diagnosis-heavy work, where the hard part is finding out what is wrong. Never offload discovery you have already done; a worker that re-reads what you read is paid-for duplication.
- Anything that needs live MCP connectors, authenticated client tools, or running app/browser state: workers cannot reach them.

For a `/offload` command invocation, explicitly set `profile: "flash"` and omit `effort`, so the configured provider-maintained DeepSeek V4.1 Flash route and its configured effort are used. The current official request ID is `deepseek-flash`; it is configuration data, not a generic provider alias to invent or send. If DeepSeek publishes a future Flash ID or changes its pricing, wait for a trusted package/config and pricing update rather than probing, guessing, or silently accepting an unpriced substitution. If the user explicitly selects a supported profile name within a `/offload` command invocation, use that exact profile instead and still omit `effort` to preserve its configured effort. DeepSeek Pro is not available through Offload at all: there is no `pro` profile, and the server rejects any Pro model id, so never request one; if the user asks for Pro, say it is unavailable and use `flash`. A provider or model name never triggers Offload or permits inferring, overriding, or inventing a profile.

Use `/offload` followed directly by the user's actual task; do not require them to paste a routing paragraph. State-changing Offload calls require normal host approval unless the user explicitly installed Offload with `node install.mjs --approval-mode=approve`; that narrow opt-in approves only Offload tools and can spend provider budget or integrate/revert a scoped patch without another prompt.

Tools (prefix `mcp__offload__` in Claude Code): `offload_start`, `offload_wait`, `offload_job`, `offload_repair`, `offload_continue`, `offload_apply`, `offload_revert`, `offload_cancel`. If tools are unavailable, `offload start|wait|job|repair|revert|cancel|retrospective` exist as shell subcommands (`offload wait` and `offload job` print the full report by default; `--detail compact` gives the lean form; `offload job <id> --include log` also takes `--tail N --limit N`); `offload_continue` and `offload_apply` are MCP tools only.

## 0. Preflight (once per session)

In Claude Code the `mcp__offload__*` tools may be deferred: listed by name only, with no schema, so they cannot be called yet. Before the first call, load them in one ToolSearch call with the query `select:mcp__offload__offload_job,mcp__offload__offload_start,mcp__offload__offload_wait,mcp__offload__offload_continue,mcp__offload__offload_apply,mcp__offload__offload_repair,mcp__offload__offload_revert,mcp__offload__offload_cancel`. A tool that is merely not loaded is not unavailable: treat the tools as unavailable only if ToolSearch returns none of them.

Call `offload_job` with no arguments. If tools or health are unavailable, say so and work directly. Pass an absolute `repoPath` when the client does not reliably supply it, and always when the task targets a repository other than the session's working directory; use that same `repoPath` for the preflight and every later call, and name it in any plan you give the user. Health must expose `server.schemaRevision: 2`, `server.capabilities.reportMode: true`, `server.capabilities.inputFiles: true`, `server.capabilities.continueJob: true`, `server.capabilities.lateApply: true`, `server.capabilities.compactReports: true`, and `sandboxReason`. If any is missing, false, or does not match this skill's supported protocol, treat the live MCP process as likely stale: do not send a report, `inputFiles`, `offload_continue`, or `offload_apply` call, tell the user to restart Claude Code/the MCP client (and, if this skill's copy is older than the server, to run `node install.mjs` from the Offload checkout), and start no Offload job of any kind until a fresh health check passes; work directly meanwhile. If `server.restartRequired` is true, follow its `restartAction`; Offload never hot-reloads or kills a client process. `staleSkill: true` (detail in `server.skill`: `installedHash`, `expectedHash`, `stale`, `state`, `reason`) means the installed skill differs from the one this server was built with: treat it exactly like a stale server (it also sets `restartRequired` and a `restartAction`: run `node install.mjs` from the Offload checkout, then restart the client). `state` `not-installed` or `unknown` is not staleness. The server independently refuses `offload_start` while either condition is stale, before creating a job or spending provider budget; that refusal is a backstop, never a reason to skip this preflight. When you stop for a stale server or skill, attribute the stop to this preflight rule (not to a user instruction), quote the health fields that triggered it (`stale`, `staleSkill`, `reason`, `restartRequired`), and end with `Offload: 0 — reason`.

Newer features are additive and gated on their own capability, not on `schemaRevision`; use one only when health reports it `true`, since an older server rejects or ignores it: `verifierDeps` (the readiness report below), `baselineVerifier` (`verifierMode`), `applyThenVerify`, `budgetSizing`, `failureDiagnostics` (`tail`/`limit`, and `offload_continue` on a `FAILED` job), `failedApply` (`offload_apply` on a `FAILED` job), `timingBreakdown` (the `time:` line and stall advisories; an older server just omits them, so do not block on it), `verifierInterpreter` (see Python verifier), `retrospective` (see Completion gate).

Health also reports, for the repository:

- `verifierTmp` (`status`, `reason`, `systemTmp`, `gitInit`): whether a sandboxed verifier can create temp directories. `status: "unwritable"` (`reason` `host-tmpdir-unwritable`: the server's `os.tmpdir()` is not writable; or `per-run-tmpdir-denied`) means no verifier can reach `DONE_VERIFIED`: tell the user and start no job with a `testCommand`. `gitInit: "failed"` means `git` cannot run inside the verifier (typically an Xcode-only host without Command Line Tools), so a suite that shells out to git fails there. `systemTmp: "denied"` is the expected, safe answer (see the temp contract below).
- `workingTree`: `clean`, counts (`changed`, `staged`, `modified`, `untracked`, `conflicted`; an untracked directory counts once, a merge-conflicted path only as `conflicted`) and a `sample` of at most five porcelain entries (for example `?? notes.txt`) with secret-shaped names left out. It shows the dirty state the worker will inherit. `clean: null` with a `reason` means git status failed. An absent field means no repository is bound (pass `repoPath`) or an older server; neither is by itself a stale-server signal.
- `verifierDeps` (see Dependencies) and `verifierPython` (see Python verifier).

The no-argument call lists only active jobs and jobs created or touched in this server session, newest first; `listing.omitted` (`omittedByScope` plus `omittedByLimit`) counts what was hidden, and `offload_job` with `all: true` (and `maxJobs`, 1-100, default 20) lists older jobs. Each row has a redacted one-line `task`, the latest round's `startedAt`, `finishedAt` and `durationSec` (elapsed so far, with `running: true`, while active), and its cumulative `costUsd` (`null`, never 0, when unknown). `listing.totalCostUsd` sums the `costUsd` of the rows returned and `listing.storeCostUsd` that of every stored job in the repository; an active job's is its spend so far, and `costUnknownJobs` counts finished jobs whose cost is malformed or was never recorded. With several repositories loaded and no repo hint, rows merge newest first and `maxJobs` caps the merged list once.

If health reports `sandbox: "policy-only"`, worker test commands are refused unless the user specifically authorizes the existing `unsafePolicyOnlyVerifier` exception. Do not add that flag merely to make a job run; expect an unverified result and perform the relevant verification yourself.

## 1. Understand and design (you)

1. Read enough to determine the design, conventions, and a real test command.
2. Write clear acceptance criteria. Keep ambiguous, architectural, and security-sensitive decisions with you.
3. For verification requests, run checks, inspect status/diff, and turn concrete defects into packages.

## 2. Decompose into work packages

- One package is one coherent change a worker can finish and verify alone.
- Every write package gets `ownedPaths`, the globs it may write (for example `src/auth/**`, `tests/auth/**`). Parallel write packages MUST have disjoint `ownedPaths`. `extraWritable` must also be disjoint from `ownedPaths` and from every other package's writable scope. `["**"]` locks the whole repo. If new tests must be registered in a runner, index, or barrel file, include that file in `ownedPaths` (or integrate the registration yourself and say so in the brief); a worker that is not allowed to edit it will leave the test unregistered.
- Shared contracts (types, interfaces, config, migrations): do them first, or put exact signatures in the brief of every package that depends on them.
- Provide `testCommand`: the narrowest command that proves the package. The server runs it itself after the worker finishes; it does not preflight or retry the command (`baseline-diff` adds one run on the start snapshot, only when the result fails). For `node --test`, pass explicit test files or quoted globs, not bare directories: current Node releases can resolve `node --test acceptance test` as module specifiers. It requires an actual macOS sandbox by default. On a policy-only host, do **not** add `unsafePolicyOnlyVerifier` merely to get a worker test: omit `testCommand`, expect `DONE_UNVERIFIED`, and run the relevant tests yourself after reviewing the integrated diff. Use a caller-supplied trusted command with explicit `unsafePolicyOnlyVerifier: true` only when the user has specifically authorized that exception; it can never repair.
- Verifier temp contract: the sandbox grants exactly one disposable per-run temp directory, exposed as `TMPDIR`/`TMP`/`TEMP` (and `HOME`) and removed when the command ends. Node's `os.tmpdir()`, `mktemp -t`, and Python's `tempfile` honor it. A test that hard-codes `/tmp` or `/var/folders`, or spawns a child with an environment that drops `TMPDIR`, fails with `EPERM` and the job ends `VERIFY_ENV_FAILED` (kind `temp-dir-denied`); `/tmp` is never widened. Fix such tests, or use `baseline-diff`. `git` works for scratch repositories under `TMPDIR` on a host with the Command Line Tools; git commands against the job's own checkout stay denied by design and fail in every run alike.
- `verifierMode: "baseline-diff"` and `verifierTimeoutSec` (5-1800; default 60 s, 300 s in baseline-diff) are optional `offload_start` parameters (CLI `--verifierMode`, `--verifierTimeoutSec`). Use baseline-diff for a repository whose suite already fails or is environment-sensitive, and run the suite yourself first to know the baseline. The server runs the `testCommand` on the result and, only if that exits non-zero, once more on an untouched private copy of the start snapshot (your dirty state included), and passes when no failing test is new. Use one test-runner invocation with node:test, TAP, jest/vitest, pytest, go or cargo output (a `;`- or `&&`-chained second command is invisible to the comparison). If the comparison cannot be made (output unparseable or incomplete, the snapshot run timed out or could not start, or the runner stopped at its first failure: pytest `-x`/`--maxfail`, cargo without `--no-fail-fast`, go `-failfast`, `--bail`, so drop the flag) the job ends `VERIFY_FAILED` with no repair round and no worker spend, and the report's `baseline-diff:` line says why. A result run that times out skips the baseline and takes the ordinary repair path (raise `verifierTimeoutSec`). It needs the macOS sandbox and cannot be combined with `unsafePolicyOnlyVerifier`; repository config cannot enable it.
- `task` is a self-contained brief: goal, design decisions, `relevantPaths` to read first, constraints, what NOT to change. `acceptanceCriteria` are checkable statements. Put in the brief what you already learned: the exact files and functions, the intended change, the edge cases to preserve, and the names of existing tests to extend, and say that this has been established so the worker should read only those files and begin writing. A brief that omits it makes the worker re-explore (in one past run, more than half of a worker's turns were repeat reads and greps). Name exact files in `relevantPaths`, and for any file over about 1000 lines give the region as `path:START-END` (1-based inclusive lines): the server converts it to a `read_file` byte offset, so the worker starts there instead of scanning the whole file, and the turn recommendation shrinks. Do not paste file contents. The server also appends one standing rule to every worker brief: assertions must be falsifiable, with no substring checks that match unrelated text; still check worker tests for tautologies in review.
- Do not hand-size turns. Set `budget.maxUsd` as the real ceiling (for example 1 to 2 USD) and omit `budget.maxTurns`: the server sizes the cap from the files in `relevantPaths` and the literal (non-glob) `ownedPaths` (`read_file` returns 24,000 characters per call, so a 14k-line file costs about 30 turns just to read), never below the configured default (80) and never above 200 on its own, and `offload_start` echoes `budgetSizing` (`maxTurns`, `turnsSource` of `default`, `scaled`, `caller` or `raised`, `recommendedTurns`, `files`, `warnings`). A plain `relevantPaths` entry means the whole file and widens a `:START-END` range on the same file; `ownedPaths` never widens one. An explicit `maxTurns` is honored exactly and warned about when below the recommendation (a cap that only covers reading ends `BUDGET` with no verifier run); `budget.turnPolicy: "auto"` makes it a floor instead. When you omit `budget.timeoutMinutes` and the expected turns (about 45 s each) would outlast the configured allowance, the server scales the stored timeout up to what they need (at most 120 minutes) and records it as `budgetSizing.timeoutMinutes`; a timeout you pass is never changed, and a warning says the job will probably end `TIMEOUT` first (then `offload_continue`). Without `server.capabilities.budgetSizing`, pass a generous explicit `maxTurns`. Do not rerun from scratch after a `BUDGET` stop: `offload_continue` keeps the work (Fix loop).
- Dependencies: the server links the primary checkout's real, gitignored `node_modules` beside the private worktree, read-only (credential-shaped files and `.cache` inside stay unreadable). Nothing else is installed or linked (no vendored caches or build outputs), and workspace/`npm link`/pnpm packages resolving outside it are not readable. Check readiness before you spend budget: `offload_job` with no jobId reports `verifierDeps` (`ok`, `partial`, `missing` with a `reason`, or `not-applicable` when the project is neither JavaScript nor Python), and `offload_start` echoes it (with `verifierDepsReason`, and `verifierDepsNested` as a count). `missing` or `partial` means a `testCommand` importing a package installed only outside the linked root `node_modules` (nested workspace sub-packages are **not** mounted) cannot pass: install dependencies in the primary first, pick a `testCommand` that does not need them, or omit it and verify yourself. An environmental failure still ends the job `VERIFY_ENV_FAILED` (see Review).
- Python verifier: the sandbox cannot read or run any virtualenv or interpreter outside the worktree (`Operation not permitted`), and the worktree has no `.venv` (gitignored). Declare it with `verifierInterpreter` (CLI flag `--verifierInterpreter`, a path or a JSON array): up to four absolute paths, each a virtualenv root or an interpreter (not a shim or script). The server resolves symlinks and grants the **verifier only** (never the worker's `run_command`, never write) read and exec of that root plus the base Python installation it needs. A declaration is refused with an error, and no job, when the path is missing, a script, inside the job's writable scope, in a credential/home/host-config area, or outside the server config's optional `verifier.interpreterRoots` allowlist. Then call it by absolute path in `testCommand` (`PYTHONPATH=src /path/.venv/bin/python -m pytest tests/x.py`): the environment is scrubbed and an editable install points at the primary, so `PYTHONPATH` must name the code under test. `offload_start` echoes `verifierInterpreter.accepted`. Health reports `verifierPython` (`ok`, `missing`, `partial`, `not-applicable`, with `reason` and a found `.venv`/`venv` as `interpreter`); an undeclared virtualenv is `missing` (`interpreter-undeclared`). To learn that it works before spending a job, call `offload_job` with no jobId and the same `verifierInterpreter`: health runs `<python> -c "import sys; print(sys.version)"` inside the sandbox and reports `ok`, or `partial` with the failure. Use it only when health reports `verifierInterpreter`.
- Set `allowNetwork` only if the package truly needs installs. Use `extraWritable` only for narrow temporary build/cache paths: its output is discarded, never integrated or reverted.

### Report / analysis packages

Use `mode: "report"` only for bounded read-and-report work whose external data is already in a caller scratch or temp directory. Omit `ownedPaths`, `extraWritable`, `testCommand`, verifier flags, and `allowNetwork`. Pass absolute `inputFiles` below the server's OS temp root. On macOS, `/private/tmp` is also accepted and `/tmp` resolves to that same root; a deployment may additionally configure a server-owned scratch root. The server size-limits and copies them read-only into the private worktree. If the pre-job rejection identifies canonical allowed roots, create the fixture below one of them and retry; do not use an arbitrary repository or home-directory path. Do not repeat source `inputFiles` paths or basenames in the task, acceptance criteria, or other durable request text; refer to the generic private manifest paths or input ordinals instead. Read `reportResult` from `offload_wait` or `offload_job` for the structured detailed text, concerns, tests, and private input paths. Report packages never integrate, cannot be repaired or reverted, and leave the primary checkout untouched.

## 3. Run

- Start independent packages together; start dependent packages after prerequisites are accepted. Every default `offload_start` must include `profile: "flash"` and omit `effort`; an explicitly selected supported profile name overrides that default. Do not substitute a model name in this field.
- Wait until each returns a final report. `offload_cancel` is an idempotent durable request, not proof that a separately owned detached worker has already stopped; after cancelling, call `offload_wait` or `offload_job` until terminal `CANCELLED` before reusing its scope.
- While workers run you may read, plan and review finished packages. Do not edit under any running package's `ownedPaths`; integration will refuse a primary-path/index/branch/HEAD conflict rather than overwrite it.

## 4. Review (you, every time)

For each final report:

1. For `mode: "report"`, review `reportResult` (not a diff): it is read-only, never integrated into the primary checkout, and cannot be repaired or reverted.
2. Verdicts: `DONE_VERIFIED` (the server's test command passed), `DONE_UNVERIFIED`, `VERIFY_FAILED` (the tests ran and failed), `VERIFY_ENV_FAILED` (the verifier could not run for an environmental reason: an unresolvable package, a missing command, a permission denial outside the job's write scope (for Python, an undeclared interpreter or virtualenv: see Python verifier), or a hard-coded system temp path: `temp-dir-denied`), `FAILED`, `TIMEOUT`, `BUDGET`, `CANCELLED`. `VERIFY_ENV_FAILED` is not a verdict on the worker's code: the server spent no repair round or budget on it, never retries it, and did not integrate it. The diff is intact; its report names the cause. A missing package can still be a worker import that does not exist, so read the diff, then use `offload_apply` (below), preferably with `applyThenVerify`. A terminal result is published only after workspace cleanup was attempted; inspect `workspaceCleanupError`, and treat `workspaceCleanupRequired` as a manual-cleanup condition. For write jobs, anything but `DONE_VERIFIED` needs action; report jobs are deliberately `DONE_UNVERIFIED` and are reviewed by their reportResult.
3. On a `FAILED` job read the report's `last failing tool call:` line first: the tool, a short argument summary (file bodies show only their size) and the underlying error, redacted, with directories shown as `<worktree>`/`<repo>`. The worker itself saw only `Tool execution failed` (plus a fixed hint for a few refusals), which is why it repeats the call. `failureKind` (`tool-loop`, `no-finish`, `output-cap`, `finish-protocol`) is present only for these worker-side failures; `finish-protocol` means the worker put `finish` in a turn with other tool calls (or with invalid arguments) twice, after one free correction in which none of that turn's calls ran, so there is no failing call to read. `offload_job` with `include: "log"` is bounded: by default the newest 60 events within 16,000 characters, behind a digest that repeats the failing call, with `logInfo` saying what was left out; identical looping turns fold into one `progress-repeat` line (`tail` counts folded lines); pass `tail` (0-1000) and/or `limit` (2,000-60,000 characters) for more.
4. For write jobs, inspect `scope`, `isolation`, and discarded ephemeral outputs. Scope violations, non-ephemeral ignored output, or a primary conflict mean nothing was applied. `offload_revert` is only available for an integrated job (including one integrated with `offload_apply`) and should be dry-run first.
5. A `DONE_VERIFIED` produced by `baseline-diff` means "no new failing tests compared with the start snapshot", not a green suite. Its `verify:` line says `via baseline-diff: N pre-existing failure(s) tolerated, 0 new` and keeps the real non-zero exit code. Report the tolerated count and never describe the suite as passing; run the failing tests yourself if a tolerated failure could hide a real regression in code the worker touched.
6. Never describe a result as verified on the strength of a worker run alone. If you integrate a diff yourself (`offload_apply`, or by hand) from a job that did not end `DONE_VERIFIED`, it was not server-verified: say so, and give the check you ran in the primary checkout (command and result) as the only evidence. For `applyThenVerify` that evidence is the recorded command, exit status and output tail in the report: say it was applied and checked by a command the server ran in the primary after applying. Prefer fixing the cause (dependencies, brief) and rerunning, or `offload_continue`, so integration stays server-verified. Never retype a diff by hand; use `offload_apply`.
7. For write jobs, read the diff (`offload_job` with `include: "diff"`; it returns only the diff, not the report again). Check against the design and acceptance criteria, conventions, error handling, security, and that tests assert real behavior. Look for scope creep, deleted or weakened tests, hard-coded values, stubs, leftover debug code.
   For algorithmic or graph/state logic, `DONE_VERIFIED` only means the supplied tests passed: run a targeted edge-case probe yourself (overlapping cycles, empty and boundary inputs, inherited/prototype keys) before accepting it.
8. Responses are compact by default (status, cost, scope, a one-line verify result with at most a 20-line failure tail, next actions); `detail: "full"` adds the full verify output, worker summary, concerns and a `timing` object. An unchanged running job polls as `unchanged: true`; wait with `timeoutSec` (0-55; a larger value is rejected) rather than polling quickly. A compact report's meta line carries the job's cumulative cost across all rounds; with more than one job touched this server session, a `spend across N jobs touched this session:` line sums them.
9. Where the time went: a terminal report carries a `time:` line splitting the wall clock into queue, setup, provider, tools, verify and finalize (longest provider and tool call; a `dominant:` bucket on a `TIMEOUT`/`BUDGET` stop or long job; compact omits it under 5 s); `detail: "full"` adds a `timing round N` line per round and your idle time. Use it, not a guess: provider-bound means a larger `limits.timeoutMinutes` or `offload_continue`; tool-bound means a smaller package or tighter command. A running job past its own limits carries an advisory stall (`level` 1 or 2, `kind`, `sinceSec`, `message`): `progress.stall` in `offload_wait` (`progress.phase` says what the round is doing), a top-level `stall` plus a `stall:` report line in `offload_job`. A new or worse stall is returned once, then `offload_wait` polls return `unchanged: true` with `progress.stalledSec`. Do not cancel on level 1 alone. `kind: "wall"` means 80% (level 1) or 95% (level 2) of the round's wall-clock allowance is used and `TIMEOUT` may follow (let it finish, then `offload_continue`, or cancel and re-scope). At level 2 consider `offload_cancel` (in-scope partial work is kept).
10. Do not trust the worker's own summary. Only the server's verify line counts. Re-run the broader suite yourself when a package touches shared code.

## 5. Fix loop

- `BUDGET` or `TIMEOUT` with in-scope changes: the work is not lost. The report's `budget stop:` line says which cap tripped (turns, usd, or reservation) with the spend so far; raise only that cap (a turn-cap stop with USD to spare needs `extraTurns` only). Review the diff, then call `offload_continue` with `extraTurns` and/or `extraUsd` for the cap that stopped the job (a `TIMEOUT` needs no increase; the clock restarts each round). It reuses the job's conversation and partial work in a fresh worktree, keeps turns and cost cumulative, consumes one of the job's repair rounds, and runs the server verifier on the result. It is refused when nothing in scope changed (start a fresh job with a better brief), when no repair rounds remain, after an unresolved capped/budget finish recovery (start a fresh job), and for any other status or failure (see the next bullet for a worker-side `FAILED`); the report lists `continue` only while it would be accepted; `offload_repair` cannot bypass a spent cap. Size the increase from what the diff still lacks, and say what is left in `note`. If you deliberately integrate a reviewed cap-stopped diff that has a configured focused verifier, use `offload_apply` with `applyThenVerify` set to that focused check; do not replace it with `verifiedBy` merely because the worker never reached finish.
- A write job that ended `FAILED` with `failureKind` `tool-loop`, `no-finish`, `output-cap` or `finish-protocol` (see Review) and in-scope changes is not lost either: read the `last failing tool call:` line, review the diff, then `offload_continue`. It needs no cap increase (pass `extraTurns`/`extraUsd` only when the report says the cumulative budget is spent), is accounted like a cap-stop continuation, and tells the worker which call failed and not to repeat it; say what to do differently in `note`. It is refused for provider or protocol failures, scope violations, a moved branch/HEAD, manual cleanup, an applied job, no repair rounds left, nothing in scope changed, or the same call looping again after an earlier round: then use `offload_repair` with a concrete change of approach, `offload_apply` if the diff is already right, or start a fresh job with a better brief.
- `VERIFY_ENV_FAILED`, a cap stop you would rather finish yourself, or a `FAILED` job whose diff is correct: after reading the diff, `offload_apply` integrates it. A `FAILED` job qualifies (health `failedApply`) when its report lists `apply` in `next:` (a non-empty in-scope diff matching the recorded snapshots; no scope violation, cleanup or integration outstanding); otherwise the error says why. `CANCELLED` and report jobs never qualify. Call it first without `apply` for a dry run (file list, the primary-conflict check and, for `FAILED`, its failure kind and reason), then with `apply: true` and either `applyThenVerify: "<the check>"` (preferred) or `verifiedBy` (a check you already ran in the primary checkout, with command and result). It applies only job-owned paths, refuses on a primary conflict, moved branch/HEAD, or index drift, and takes the job's write lease. Either way the job becomes `DONE_UNVERIFIED`, never `DONE_VERIFIED`: the report states it was applied without server verification (for a `FAILED` job, with its original failure) and quotes your check; `offload_revert` undoes it.
  - `applyThenVerify` applies the diff, then runs your command in the primary checkout under the macOS sandbox with the checkout **read-only** (writes only to a per-run temp dir, no network even for a job started with `allowNetwork`, `.git` and secret files unreadable), so a suite that writes into the repo tree or shells out to git fails there; use `verifiedBy` for those. A job's declared `verifierInterpreter` applies there too. On exit 0 the job is `DONE_UNVERIFIED` with the command, exit status and output tail recorded as your check. On a non-zero exit, a timeout, a cancel, or a command that cannot start, the server reverts the diff, proves the primary's job-owned paths are back as they were, and returns `applied: false, reverted: true` with the failing output tail (a normal result, not an error: check `applied`); the job stays apply-eligible, so fix the cause and call it again. `applyThenVerifyTimeoutSec` is 5-900 (default 300) and the run holds the job's write lease. The call blocks for the whole run, so your host's tool timeout bounds it (the managed Codex config uses 60 s) and a client-side cancel aborts the command and reverts the diff: keep the check short, or use `verifiedBy`. If your call times out, `offload_wait` shows `progress.applyThenVerify` and `offload_job` a top-level `applyThenVerify.phase`; `offload_cancel` (from any process) stops the command and reverts the diff.
  - If the call fails with an error saying the automatic revert did not complete, or `PRIMARY_CHANGED`, the diff is **still applied** (the job is `DONE_UNVERIFIED`): inspect the primary, dry-run `offload_revert`, and never claim success. Do not edit the job's paths while the run is in progress. A server restart mid-run is reconciled from the live tree and reported `INTERRUPTED`; it is never a pass.
  - On a policy-only host `applyThenVerify` is refused, like a `testCommand`. Pass `unsafePolicyOnlyVerifier` only when the user specifically authorized that exception (the command then runs unsandboxed in the primary); otherwise run the check yourself and pass `verifiedBy`.
- Concrete verifier/test defects: call `offload_repair` with the job id and a precise list (file, symptom, expected behavior) only when the verifier actually ran in the macOS sandbox and the job was not applied. After a `baseline-diff` failure, the automatic repair names only the new failures; pre-existing failures are never repair targets, and an inconclusive comparison is not repairable (fix the runner output or the timeout, then start again). Use at most three rounds per package. The following transient-provider-failure rule is the explicit exception when no verifier ran.
- A write job that ended `FAILED` or `TIMEOUT` with a transient `providerFailure` (attempt timeout, transport, or retryable HTTP status) was not applied. After reviewing its diff/status, a manual bounded `offload_repair` may start another normal worker pass only when its cumulative budget and repair-round allowance remain. Do not treat that new pass as free, do not auto-retry a provider failure, and never repair a report job. Do not use repair to retry deterministic request/redirect/SSE-protocol failures.
- A provider `attempt_timeout` is a single request deadline, distinct from the job's wall-clock budget. `providers.<name>.attemptTimeoutMs` is 30,000–600,000 ms and defaults to 300,000 ms. Terminal job metadata and its report expose the numeric limit; do not assume a timed-out POST was free or automatically replay it. The default per-job wall-clock allowance is 30 minutes (`limits.timeoutMinutes`), restarted for each round. A worker's own `run_command` is capped at 900 s (a longer request is clamped to 900).
- A tiny integration fix you may make yourself; say so in the final answer.
- Two failed rounds on the same defect usually mean the design or brief is wrong. Fix that, retry once, then do it yourself or report the blocker.
- If an integrated job went wrong beyond repair, dry-run then apply `offload_revert`; otherwise restart the package with a better brief. Cancelled and failed jobs retain a review patch but were not applied automatically.

## 6. Completion gate

Do not give your final answer until all hold, or you state exactly which does not and why:

- every write package is `DONE_VERIFIED` (or verified by you, and stated as such if integrated with `offload_apply`; an `applyThenVerify` counts as your check, so quote its command and exit status), and every report job is reviewed `DONE_UNVERIFIED`, with its reportResult reviewed;
- no scope violations, stray files, or unexpected branch/HEAD change;
- the whole project's build, tests and lint pass (run them);
- nothing the worker listed under concerns is left unaddressed;
- for a `/offload` command invocation only, and when health reports `retrospective`: call `offload_job` once with `include: "retrospective"`, your `repoPath` and `jobIds` of every job you started. Its `signals` are server-derived leads, not verdicts; `maintainerPromptWarranted`, `reasons` and `maintainerPromptSkeleton` are a starting point. Weigh them with what you saw (what worked, what you did by hand, what wasted spend or time): a weak result from a thin brief, a cancel you chose or a provider failure is not an Offload defect. After your answer and before the routing line, put either `Offload retrospective: nothing to improve` or a fenced block headed `Maintainer prompt (paste into the Claude Code session that maintains Offload)`: the skeleton edited with your own evidence, numbered requests, at most 40 lines, no secrets, source or diffs. The prompt is for the user to paste: never edit the Offload repo, config or skill because of it. With `Offload: 0`, skip the call unless health or tooling failed (then use its health facts alone).

Then answer briefly: what changed (files, one line each), how it was verified, what you reviewed or fixed yourself, anything left for the user. Never paste worker transcripts or full diffs. For a `/offload` command invocation, end every final answer with one standalone routing line: `Offload: N jobs` when jobs started, or `Offload: 0 — reason` when none fit, tools/health were unavailable, or the work was done directly.

## Rules that do not bend

- Never delegate architecture, ambiguous requirements, security-sensitive decisions, or the final review.
- Never run two workers on overlapping paths. Never edit under a running worker's `ownedPaths`.
- Never tell the worker to commit, push or switch branches. Commit only if the user asked, and only reviewed files.
- Never report success on the worker's word.
- If the user says "solo", "no offload" or "do it yourself", stop delegating.
